Engine Architecture

How the data described in Data Model gets turned into sound, and how the UI and the real-time audio thread share it.

Data model vs. real-time engine

src/main.rs (egui/eframe UI) owns the live Song behind Arc<Mutex<Song>>, shared with the real-time audio thread — UI edits and audio playback both read/write through that same lock. src/audio.rs is the real-time engine: cpal stream setup, the step/tick clock, per-track voice pools, and the offline WAV exporter (render_song_to_wav), which reuses the exact same Sequencer::process synthesis path as live playback but runs its own separate wet mixdown (mix_song_to_wav_buffer) — deliberately not shared with build_playback_stream's live mixdown, so nothing in the bounce can regress real-time playback.

Voice pools

Each track gets four always-allocated voice pools in TrackVoices: voices (Simple engine), trine_voices (Trine), wave_voices (Wave), and sample_voices (one-shot WAV playback). A track's synth_engine selects which pool its notes/steps trigger; idle pools just contribute silence. src/factory_presets.rs holds the built-in preset catalog for all three engines.

Stereo signal path (dual-mono)

The engine is genuinely stereo end to end, built from independent per-channel state rather than panning a mono sum:

  • Every voice type's next_sample() returns (left, right). Simple/Wave spread unison voices across the stereo field via unison_width; Trine has no unison, so its width instead comes from running its entire chain (oscillators, FM, ring mod, both filters) twice with independently-seeded analog drift.
  • Track::pan (equal-power) is applied once, after a track's effects chain.
  • src/plugin_host.rs's process_effect_chain carries real L/R between chain stages; a stage only loses width if that specific plugin declares mono I/O.
  • src/builtin_fx/ implements every built-in effect as dual-mono: independent per-channel state, sharing only immutable parameters and sample rate.

Effects and plugin hosting

src/builtin_fx/ is the native effect DSP, one file per effect, aggregated in mod.rs as the BuiltInEffect enum. src/plugin_host.rs hosts CLAP plugins — loading, activating, querying ports/parameters, running audio, host-side parameter editing, no unload mid-session. A loaded plugin's GUI can be embedded (drawn into a host-owned native container view, src/gui_embed/, per-platform Cocoa/Win32/X11 — no Wayland) or floating, tried in that order by plugin_host::open_plugin_gui; only the macOS embedding backend has actually been run.

The master bus has its own chain (Song::master_effects, via plugin_host::process_effect_chain), mixing CLAP and built-in effects exactly like a track's chain — MasterEffectSlots is a type alias for TrackEffectSlots pinned to one row.

A track's post-fader/pan signal sums into its chosen submix's own accumulator (or straight into master if TrackOutput::Master); each submix then runs its own chain and volume before summing into master. Sends tap the same post-fader/pan point in parallel, in build_playback_stream's mixdown — the same point LoudnessMeter reads from (src/metering.rs). Mute/solo are enforced earlier, at synthesis time in Sequencer::process's track_silent — soloing/muting a submix acts like soloing/muting every member track at once.

render_song_to_wav (the offline bounce) runs every send's and submix's own chain too, via a temporary plugin_host::OfflineEffectChain loaded fresh for the bounce's own sample rate — a separate mixdown path from live playback's, not build_playback_stream itself. The bounce does not, however, consult track/submix mute or solo — every track always renders there.

Sidechain routing

TrackEffectConfig::Clap/Compressor/NoiseGate each carry a sidechain_source: Option<usize> — an index into Song.tracks whose pre-effects signal is threaded alongside the normal signal (all_track_dry) so that slot's envelope follower (or, for CLAP, its second input port) reads a different track's level. Silently ignored if the target doesn't declare a second input. The CLAP sidechain path is implemented but not verified against a real sidechain-capable plugin.

Freeze / bounce-in-place

Track::frozen/frozen_clip reuse AudioClip rather than introduce new runtime state: freezing renders the track's live output (including its own chain) to a clip, then plays that back with the chain bypassed. Unfreezing needs apply_chain_specs_at to resync the live chain state before it's active again.

Plugin delay compensation

A per-track DelayLine compensates for a latent effect (a look-ahead limiter, or a CLAP plugin that reports nonzero latency) so every other track still lines up in time. Live playback recomputes compensation as chains change; the offline bounce computes it once up front. Sends and master are excluded from compensation. CLAP latency querying is implemented but unverified against a real plugin that reports it.

Region fades and automation ("rides")

Region::fade_gain_at is applied per-tick inside Sequencer::process (Sequencer::track_fade_gain) since it has to scale already-triggered, freely- ringing voices. An AutomationLane lives on either Region::automation (region-local ticks, only while that region is active) or Track::automation (absolute song ticks, always in effect) — where both target the same parameter at the same tick, the region's own lane wins, resolved by audio::collect_automation applying track-wide lanes first, then the active region's.

Automation is evaluated sample-accurately, not once per buffer: collect_automation resolves every track's active lanes into per-target LaneRefs once per buffer, then the mixdown calls LaneRef::value_at per output sample for Volume/Pan/SendLevel targets, while process_chain_with_automation sub-chunks the buffer at every breakpoint inside it for EffectParam targets — a breakpoint-rate approximation shared by CLAP and built-in effects (not literal per-sample plugin-event timing). Built-in param automation goes through builtin_fx::automatable_params_for_config/set_automatable_param; CLAP param automation reuses LoadedEffect::set_param_by_id.

Audio clips: trim, fades, Take Folders, Flex Time/Pitch

Unlike a Region's per-tick fade, an AudioClip's fade ramps per-sample inside SampleVoice — trigger_clip windows playback to source_start_frame..end_frame and carries fade_in_frames/ fade_out_frames, computed from the clip's tick-domain fields at the tempo in effect at its trigger tick.

Take Folder playback is a second trigger loop in Sequencer::process, right next to the plain-AudioClip one: each comp segment triggers a SampleVoice windowed into its own take's buffer exactly like a trimmed clip, with a fixed 5ms auto-crossfade (TAKE_FOLDER_CROSSFADE_SECONDS) at every segment boundary.

src/stretch.rs (WSOLA time-stretch) and src/pitch.rs (pitch detection/shifting) are pure, hand-rolled DSP baked into the decoded buffer once at load time (AudioClip::load) rather than done live — the same "print once, play back through the ordinary path" approach transient_detection::detect_non_silent_segments's Strip Silence already uses, so SampleVoice, trim/fades, and the offline bounce need zero changes to support either feature. Pitch-shifting resamples a segment by the target ratio first, then WSOLA-stretches it back to the original length. Functionally verified (target duration/frequency hit, silence stays silent, no NaNs) but not verified by ear.

Groove: quantize, humanize, groove templates

src/groove.rs is pure data mutation — no audio, no UI — over a region's Vec<Note> and a lane's Vec<Option<StepData>>, both sharing one GROOVE_TEMPLATES catalog (Straight, Swing 8th Light/Heavy, Swing 16th Light, MPC Push, MPC Lay-back) so the two editors never drift apart. Humanize's jitter is a small dependency-free integer hash (signed_jitter), not rand — deterministic given the same seed. audio::step_triggering_at checks the two step boundaries nearest the current tick (rather than exact modulo) so a nudged step still fires at its own adjusted tick — the same function used live and in the offline bounce.

Tempo: tap tempo, audio detection, tempo map

The real-time engine applies two precision levels rather than one sample-accurate rewrite: Sequencer::process's tick clock re-resolves bpm_at at every tick boundary (exact per-tick trigger precision, using the tick that just fired's own tempo). Continuous automation and the offline bounce instead resolve tempo once per audio buffer/render chunk — a few milliseconds of possible latency on a tempo change, traded for not rewriting the sample-accurate automation math for a per-sample-varying rate. render_song_to_wav's total-length calculation (audio::samples_for_tick_span) sums each constant-tempo segment's own duration, so a bounce comes out the correct length across a tempo change.

src/tempo.rs's TapTempo averages up to 8 recent taps, auto- resetting after a 2-second pause. src/tempo_detection.rs's detect_bpm is a time-domain onset detector (energy envelope → novelty → adaptive-threshold peak-picking → inter-onset-interval histogram vote, octave-folded into 60–180 BPM) — good for clearly rhythmic material, not a spectral beat tracker for a dense mix. There's no automatic tempo-curve derivation from a recording (true beat-tracking across drift was cut from scope).

MCP control

src/bin/simple-daw-mcp.rs is a standalone MCP server binary (Unix only) that speaks MCP over stdio and forwards tool calls as opaque JSON over a Unix domain socket to src/mcp_control.rs inside the main binary, which queues them for the UI thread to apply on its next frame (several commands need to stay in lockstep with UI-only bookkeeping only that thread touches).
